# 資料管理:從下載到正式環境的管線

**Docker 映像檔**:`ml4t`

**第 2 章:金融資料的全貌**

前面的筆記本抓取並驗證了資料。本筆記本說明如何使用 ml4t-data 的正式環境功能,大規模地**管理**資料:

- **DataManager**:抓取、儲存與更新的統一進入點
- **Universe**:預先定義的代號清單(S&P 500、NASDAQ 100 等)
- **HiveStorage**:分割的 Parquet,供快速查詢與增量寫入
- **增量更新**:不必重新下載歷史就能讓資料保持最新
- **CLI**:供腳本化流程使用的命令列介面

## 學習目標

完成本筆記本後,你將能夠:
1. 以 `DataManager` 作為所有資料操作的單一進入點
2. 用 `Universe` 類別載入預先定義的股票池
3. 以 Hive 分割的 Parquet 儲存與查詢資料
4. 執行增量更新並偵測缺口
5. 使用 `ml4t-data` CLI 進行腳本化流程

## 為什麼這很重要

一次性的下載對教學來說沒問題。但交易系統需要:
- **每日更新**,只抓取新資料(比完整重抓快 10 倍)
- **分割儲存**,支援快速的日期範圍查詢
- **缺口偵測**,在回測之前確保資料完整
- **中繼資料追蹤**,讓你知道自己有什麼、何時更新過

> **ml4t-data 文件**:完整參考請見[增量更新指南](https://ml4trading.io/docs/data/user-guide/incremental-updates/)與[儲存指南](https://ml4trading.io/docs/data/user-guide/storage/)。

**先備條件**:已安裝 ml4t-data;可即時連線到 Yahoo Finance。

## 1. DataManager:統一的進入點

`DataManager` 把供應商選擇、儲存與更新都放在同一個介面後面。比較一下:

```python
# 沒有 DataManager(手動)
provider = YahooFinanceProvider()
df = provider.fetch_ohlcv("AAPL", "2024-01-01", "2024-12-31", "daily")

# 使用 DataManager(統一)
dm = DataManager()
df = dm.fetch("AAPL", "2024-01-01", "2024-12-31")
```

它真正的威力展現在批次操作、儲存整合與更新上。

## 3. HiveStorage:分割的 Parquet

對於你會反覆查詢的資料,Hive 分割的 Parquet 是 ml4t-data 全面採用的儲存層。HiveStorage 後端把像 `equities/daily/AAPL` 這樣的邏輯鍵,編碼成對檔案系統安全的目錄名稱,並在底下巢狀地放置 Hive 風格的年與月分割:

```
hive_demo/
├── .metadata/
│   └── equities_daily_AAPL.json
└── equities_daily_AAPL/
    ├── year=2024/month=1/data.parquet
    ├── year=2024/month=2/data.parquet
    └── ...
```

**相較於單一檔案的好處**:
- **分割裁剪**:查詢「最近 30 天」只讀 1 個檔案,而不是全部歷史
- **增量寫入**:新資料直接附加,不必重寫既有的分割
- **中繼資料追蹤**:知道每個代號上次更新的時間

### 檢視分割結構
=====902e23bb
目錄名稱無法從外部直接定址:鍵是為了檔案系統安全而編碼過的,而且每次寫入都會提交到一個新的世代(generation)目錄,這樣失敗的寫入就不會留下一個寫到一半、卻看得見的分割。因此,呼叫者是透過 `partitions()` 來詢問儲存層寫了什麼,而不是去列出一個自己猜的路徑。

## 4. 增量更新

關鍵的工作流程:歷史資料下載一次,之後**每天只更新**新資料。
=====5af4cc4b
### 更新一個代號

增量是自上次儲存的 K 棒以來的所有資料,直到供應商實際已經發布的最新一根 K 棒為止。這個上限不是可有可無的:Yahoo 會把目前的交易所日期回傳成一列成交量持續累積、但沒有開高低收的資料,而供應商類別會拒絕價格為空值的 K 棒。`DataManager.update()` 會抓取到 `datetime.now()`,所以它在每個交易日都會要求那一列。`update_through_last_complete_bar` 要求的是同樣的增量,但它是去找出視窗的終點,而不是計算出終點——只要供應商拒絕該視窗,它就一次往回退一天,因為那個佔位列通常在收盤後幾小時就會補上,但有時不會。被拒絕的視窗會以 error 層級記錄,所以一行錯誤訊息後面跟著一個列數,代表的是回退機制在運作,而不是失敗。
=====672d44b4
### 了解更新策略

ml4t-data 支援四種更新策略:

| 策略 | 行為 | 使用情境 |
|----------|----------|----------|
| `INCREMENTAL` | 只抓取上次儲存的時間戳記之後的資料 | 每日更新(預設) |
| `APPEND_ONLY` | 絕不修改既有的資料列 | 可供稽核的封存資料 |
| `FULL_REFRESH` | 取代該代號的所有資料 | 資料損毀後的復原 |
| `BACKFILL` | 填補歷史資料中的缺口 | 修補缺漏的期間 |

預設的 `INCREMENTAL` 策略對大多數工作流程都是正確的。`DataManager.update()` 會自動使用它。
=====b660cff5
### 缺口偵測

`exclude_weekends=True` 讓週六與週日不被算成缺口,這是偵測器在沒有被提供行事曆的情況下,唯一能自行推斷的交易行事曆部分。

因此它回報什麼,取決於它拿到的序列是什麼形狀,而兩種形狀會給出相反的答案。這裡快取的序列是日曆上稠密的:每個非交易日都把前一個收盤價往後帶,所以沒有任何缺漏可找,偵測器回報沒有缺口。一個只帶有交易日的稀疏資料饋送,則會讓偵測器標記每一個假日,因為對任何沒有交易所行事曆的東西來說,假日與資料中斷是同一種缺漏。兩個答案都沒有錯,但也都不能單獨當成涵蓋率檢查。

在回測之前,請先驗證資料的完整性。IncrementalUpdater 可以偵測缺少的交易日。

## 5. 命令列介面

ml4t-data 包含一個 CLI,供腳本化流程與 cron 排程使用。以下是主要的指令:

### 抓取資料
```bash
# 單一代號
ml4t-data fetch AAPL --start 2024-01-01 --end 2024-12-31

# 多個代號
ml4t-data fetch SPY QQQ IWM TLT --provider yahoo --output data/etfs.parquet
```

### 更新已儲存的資料
```bash
# 更新一個代號(增量——只抓取新資料)
ml4t-data update AAPL --storage-path ./data

# 更新所有已儲存的代號
ml4t-data update --all --storage-path ./data
```

### 驗證資料品質
```bash
# 對已儲存的資料執行 OHLCV 驗證
ml4t-data validate ./data/etfs.parquet
```

### 列出可用的資料
```bash
# 列出儲存中的代號
ml4t-data list --storage-path ./data

# 列出可用的供應商
ml4t-data info --providers
```

### 自動化每日更新(Cron)
```bash
# 週一到週五,美東時間每天下午 6 點(美股收盤後)
0 18 * * 1-5 cd ~/ml4t && ml4t-data update --all --storage-path ./data >> logs/update.log 2>&1
```

以下是結合上述一切的完整工作流程——也就是本書 `data/download_all.py` 協調程式所採用的模式。
=====253ffe63
上面印出的問題數量,是極端報酬檢查被觸發,而不是資料損毀。驗證器設定了每日最大變動幅度,而在一年期的 ETF panel 上,每個序列中最大的那次變動就是它標記的對象。這是檢查在正常運作:它把候選項目浮現出來,但完全沒有說明其中哪些是缺陷。

決定如何處置候選項目是另一個步驟,而它屬於有脈絡可循的下游。`13_data_quality_framework` 正是拿同一個檔案的公司行動欄位來為這類標記評分,而這就是候選清單與缺陷清單之間的差別。

## 總結

| 元件 | 用途 | 主要方法 |
|-----------|---------|------------|
| **DataManager** | 統一的進入點 | `fetch()`、`batch_load()`、`load()`、`update()` |
| **Universe** | 預先定義的代號清單 | `Universe.SP500`、`Universe.get("nasdaq100")` |
| **HiveStorage** | 分割的 Parquet | `read()`、`write()`、分割裁剪 |
| **GapDetector** | 時間序列的缺口偵測 | `detect_gaps()`、`detect_gaps_in_storage()` |
| **CLI** | 腳本化流程與 cron | `ml4t-data fetch`、`ml4t-data update` |

### ml4t-data 的工作流程

```
1. 初次載入:    dm.load("AAPL", "2020-01-01", "2024-12-31")
2. 每日更新:    dm.update("AAPL", lookback_days=7)
3. 缺口檢查:    gap_detector.detect_gaps(df, frequency="daily")
4. 批次載入:    dm.batch_load_universe("sp500", start, end)
5. 自動化:      cron + ml4t-data update --all
```

### 重點整理

- **一個進入點,多個供應商。** `DataManager.fetch()` 隱藏了資料究竟來自 Yahoo、Binance、AlgoSeek 還是本機的 Hive parquet;供應商換了,使用者的程式碼不必改。
- **`load()` 以快取優先,`fetch()` 以供應商優先。** 研究/回測用 `load()`(快速、離線、可重現);只有在必須更新快取時才用 `fetch()`。
- **股票池是一等公民。** `Universe.SP500` 等等讓代號清單不必出現在筆記本程式碼中,並在函式庫裡受版本控制。
- **缺口偵測是另一項獨立的工作。** `GapDetector` 是對已儲存的資料執行的;缺少的交易日會以發現的形式浮現,而不是無聲的空值。
- **CLI 是正式環境的操作介面。** 由 cron 驅動的 `ml4t-data update --all`,與筆記本所執行的是同一條程式路徑。
