# 儲存效能測試:資料庫引擎

**Docker 映像檔**:`benchmark`

> **需要 Docker**:本筆記本依賴 `benchmark` 環境與資料庫服務。執行方式:
> ```bash
> docker compose --profile benchmark up -d timescaledb clickhouse questdb influxdb
> docker compose --profile benchmark run --rm benchmark python 02_financial_data_universe/21_storage_benchmark_database.py
> ```

**重點**:可查詢的金融時間序列資料庫

## 資料庫類別

| 類別 | 範例 | 特性 |
|----------|----------|-----------------|
| **內嵌式** | SQLite、DuckDB、ArcticDB | 在行程內執行,不需要伺服器 |
| **時間序列伺服器** | ClickHouse、QuestDB、TimescaleDB | 正式環境規模,需要 Docker |
| **通用型** | PostgreSQL、InfluxDB | 作為比較基準 |
| **高頻交易專用** | kdb+/PyKX | 交易業界的標準 |

## 測試的操作

1. **寫入**——大量插入的效能
2. **讀取**——全表掃描
3. **範圍查詢**——7 天的時間視窗(回測的工作流程)
4. **OHLCV 彙總**——把分鐘 K 棒重新取樣成日 K 棒
5. **ASOF Join**——成交與報價的對齊(對微結構研究至關重要)

## 計時政策

一套政策,一視同仁地套用在每個引擎上。在不同規則下計時的引擎不該出現在同一張圖上,所以規則在這裡說明,並由 `time_write` / `time_read` 輔助函式強制執行,而不是靠每次呼叫的參數:

- **寫入**(`time_write`)——只做一次、沒有暖身,寫入為這次執行全新建立的資料表。大量載入是每個資料集只發生一次的事,所以我們計時的就是這個。重複執行會在只能附加的引擎上附加重複的資料列,或者需要一個不屬於寫入本身的清除步驟。
- **寫入的長條是用戶端付出的成本,而各用戶端並不相同。** SQLite、DuckDB、ClickHouse 與 kdb+ 是整塊接收 panel(`to_sql`、Parquet 掃描、`insert_df`、`set`)。PostgreSQL 與 TimescaleDB 必須為 `execute_values` 每列建立一個 Python tuple,InfluxDB 則必須為 line protocol 每列建立一個 `Point`。這種建構是使用那些介面的代價,所以它留在計時區域之內,而這三者也各自單獨量測它並印出所佔比例;圖表上方的表格把它們彙整起來。那三個數字只是*明確寫出*的逐列建構,別無其他。每個用戶端都會在某處做轉換與序列化——`to_sql` 仍然要準備並綁定每一列,`insert_df` 仍然要序列化資料表——而這些從外部都無法分離出來,所以一根沒有量測到比例的長條,並不代表它全部是引擎的時間。請把每一根寫入的長條讀成「透過 Python 用戶端把這份 panel 放進這個引擎的成本」,絕不要讀成引擎的匯入速率。
- **計時區域內包含持久性。** PostgreSQL 與 TimescaleDB 是同步提交,所以它們的刷寫成本在計時的呼叫之內。QuestDB(ILP + WAL)與 InfluxDB 會在資料列可以查詢之前就回覆確認,所以它們在計時的呼叫*之內*,透過 `wait_until_rows_visible` 輪詢到第一次可查詢為止。因此每個寫入時間都結束在同一個事件:資料已持久化且可讀取。
- **讀取、彙總與 join**(`time_read`)——在一次不計時的暖身之後,取 `TIMING_RUNS` 次執行的平均。**這些是暖的數字**,作業系統頁面快取與各伺服器的緩衝池都是暖的,而它們對每個有快取的引擎都有利。用戶端無法清除伺服器的快取,所以這裡的「冷」讀取對內嵌式引擎是冷的、對伺服器卻是暖的——既不冷也無法比較。暖而一致才是可量測的選擇;§2.4 在報告這些數字時有說明這一點。
- **每次讀取都會驗證**是否與預期的列數完全相符。下面的每個查詢都是確定性的,答案在執行之前就已知,所以差一點點就是錯誤的答案,而不是可以容忍的答案——否則一個默默回傳截斷結果的查詢,就會在圖上拿下最快的時間。

## 大小欄位代表什麼、不代表什麼

與計時不同,磁碟上的大小**並不是**以相同的方式為每個引擎量測的,因為每個引擎只提供它自己的統計方式。請把大小欄位讀成「這個引擎回報它正在使用的空間」,而不是同基準的壓縮比:

| 引擎 | 回報來源 | 計入 |
|--------|-------------|--------|
| SQLite / DuckDB | 磁碟上的檔案大小 | 資料庫檔案 |
| ClickHouse | `system.parts.bytes_on_disk` | **壓縮後**的資料分段 |
| QuestDB | `table_storage().diskSize` | 該資料表在磁碟上的完整佔用空間 |
| PostgreSQL / TimescaleDB | `pg_total_relation_size` / `hypertable_size` | 資料表**加上索引**(對 hypertable 而言,還包括它所有的區塊) |
| InfluxDB | *未提供* | 用戶端 API 不回報每個 bucket 的大小,所以留空,而不是記錄為零 |

拿 ClickHouse 壓縮後的分段去比 PostgreSQL 的資料表加索引總和,並不是壓縮率的比較。檔案格式的筆記本(`20_storage_benchmark_file`)才是對各比較對象以相同方式量測大小、可以直接比較的地方。

## 快速開始

```bash
# 只跑內嵌式引擎。DuckDB 與 SQLite 除了基本安裝之外不需要別的。
uv run python 02_financial_data_universe/21_storage_benchmark_database.py

# 連同伺服器引擎一起跑,從主機執行(compose 會發布它們的連接埠)
docker compose --profile databases up -d timescaledb postgres clickhouse questdb influxdb
uv run --extra db-benchmark python 02_financial_data_universe/21_storage_benchmark_database.py
```

`db-benchmark` 這個 extra 也包含 ArcticDB,而它沒有發布 Linux ARM64 的 wheel,也沒有原始碼發行版。在 ARM64 上,安裝會在筆記本能執行之前就失敗,所以選用匯入的防護根本沒有機會跳過它:請改用上面的 Docker 路徑,它的 `benchmark` 映像檔包含伺服器用戶端,但不含 ArcticDB。

規模是下面的 `BENCHMARK_SCALE` 參數,不是環境變數:參數儲存格之後的那個儲存格會把參數寫回環境變數,供 `utils.storage_benchmarks` 讀取,所以在命令列上加 `BENCHMARK_SCALE=...` 前綴,會在任何東西讀取它之前就被覆寫。要更改規模,請編輯參數,或像 CI 那樣用 Papermill 注入。

不論有哪些引擎回應,接近最後的涵蓋報告都會列出產生這一頁數字的引擎,以及沒有產生的引擎。

## 環境設定
=====c81c3d64
### 宣告的參數

`BENCHMARK_SCALE` 選擇 panel 的大小;正式設定是 §2.4 所引用的那一個,CI 則透過 Papermill 把它覆寫成小規模。每個回報數字的儲存格也會回報產生它的規模,所以從這一頁取走的數字會帶著自己的出處。

`RANGE_QUERY_SHARE` 是範圍查詢應該選取的 panel 比例。它是比例而不是固定的天數,因為 panel 的日曆跨度會隨規模增長:固定的七天視窗選到的是大 panel 的五分之一,卻是小 panel 的*全部*,那會默默地把圖表中的範圍查詢那一格變成全表掃描的第二份副本。

`LOG_AXIS_RATIO` 是圖表的某一格切換成對數 x 軸的差距門檻,依實際畫出的長條量測,而不是依過去某次執行的結果來假設。
=====d2efe42a
`utils.storage_benchmarks` 在被匯入時會從環境變數讀取規模,所以這個變數必須在匯入之前設定,而不是事後再傳給函式。
=====ffffb777
## 檢查可用的資料庫
=====065f2c1b
### 有哪些引擎

DuckDB 同時包含在 `benchmark`(ARM64)與 `benchmark-full`(x86)映像檔中,SQLite 則隨 Python 而來,所以兩者永遠可用;沒有 DuckDB 時,筆記本會拒絕繼續,而不是默默把它略過。ArcticDB 只支援 x86,位於 `benchmark-full`;沒有它的地方就回報為不存在。
=====d7f9a7bc
下面 ArcticDB 的防護捕捉的是 `Exception`,不是 `ImportError`。一個已安裝但無法執行的 ArcticDB 會拋出完全不同的錯誤——例如遇到不支援的 protobuf 時的 `NotImplementedError`——而只捕捉 `ImportError` 的防護會讓那個錯誤終止整本筆記本。一個選用的引擎,必須在它可能無法使用的每一種方式上都是選用的,而不只是在它可能不存在的那一種方式上。
=====e9d4e150
### 透過 PyKX 以 IPC 模式使用 kdb+

q 的執行檔與授權是在匯入 PyKX *之前*尋找的,而這個順序是關鍵。PyKX 絕對不能在無授權模式(`PYKX_UNLICENSED=1`)下匯入。無授權的匯入會讓行程處於一種之後做 numpy 運算會發生區段錯誤(segfault)的狀態,而當機會落在 `generate_ohlcv_data` 裡,離造成它的匯入很遠,所以讀起來像是資料的錯誤。沒有授權就沒有東西可以測試,所以完全不匯入 PyKX,並跳過 kdb+。
=====60cdea08
`expected` 標記某個引擎是本章要比較的對象。`available` 表示它在這台機器上通過了可用性檢查。這是兩個不同的問題,把它們混為一談,會讓一台沒有執行 Docker 的筆電變成一次回報五項失敗的執行。下面的三個數量,以及最後的涵蓋報告,都是從狀態表讀出來的,而不是寫成固定數字,所以新增一個引擎時,把它加進那張表就完成了大部分的工作。
=====3d5db9b0
## 產生測試資料
=====e4cfa235
### 量測明確寫出的逐列建構

PostgreSQL、TimescaleDB 與 InfluxDB 是透過每列需要一個 Python 物件的介面連到它們的伺服器,所以建立那些物件是透過它們寫入的成本的一部分,並且留在計時的寫入之內。由於那項建構是一個獨立的運算式,它也可以單獨計時,下面的輔助函式就是這麼做的。得到的結果是這三個用戶端各自所佔比例的下界,而不是全部:用戶端仍然要轉換並序列化它拿到的東西,每個介面接收整個資料表的用戶端也是如此。這裡沒有量測那一部分。
=====279a9003
## 測試視窗

兩個衍生的量,下面每個引擎都會重複使用,這樣所有引擎回答的是*同一個*問題,並且可以對照相同的預期列數來驗證:

- **範圍查詢**:panel 最前面的幾個交易日,也就是回測會走過的那一段。視窗的大小是 panel 的一個比例,而不是固定的日曆天數,因為 panel 的跨度是規模的函數。七個日曆天是大 panel 的五分之一,卻涵蓋了整個小 panel,而一個選取每一列的範圍查詢,只是換了名字的全表掃描:圖表會顯示兩格在量測同一個查詢,而讀者沒有辦法分辨。依比例決定大小,能讓問題在每個規模下都相同,而下面的儲存格會印出它實際達到的比例。
- **彙總**:把分鐘 K 棒重新取樣成**日** K 棒。每個引擎都是依日分桶;如果把分鐘資料依分鐘分桶,對這麼做的引擎來說幾乎是恆等操作,對沒這麼做的引擎則是真正的縮減,那就不算是比較。

# 第 1 部分:內嵌式資料庫

=====43f7d4c0
## SQLite(內嵌式關聯資料庫)

SQLite 是內嵌式的關聯資料庫:
- 符合 ACID,單一檔案的資料庫
- 適合交易型工作負載(OLTP)
- 分析型查詢的最佳化有限
- 沒有原生的 ASOF join
=====e263499d
### SQLite 的讀取與彙總
=====be7de228
### SQLite 範圍查詢

SQLite 把時間戳記存成 ISO-8601 文字,而它可以依字典順序排序,所以下面的字串界限會用到涵蓋索引 `(symbol, timestamp)`。
=====de390a7a
### SQLite OHLCV 彙總

`open` 是該交易日依時間排序的第一個價格,`close` 是最後一個——而不是 `MIN(open)` / `MAX(close)`,那是另一個(而且是錯的)統計量。SQLite 沒有 `first`/`last` 彙總函式,所以 OHLCV 的彙總需要用到視窗函式。這讓 SQLite 相對於有原生 `first`/`last` 的引擎多花了時間,而那個成本就是「這項彙總在 SQLite 上要花多少?」的誠實答案。
=====d4e57a8d
## DuckDB(內嵌式分析)

DuckDB 是為分析型工作負載(OLAP)設計的:
- 欄式儲存、向量化執行
- 原生支援 ASOF join(v1.1 起)
- 從 Parquet 零複製讀取
- 可對大於記憶體的資料做核外(out-of-core)處理
=====85ddc12a
## ArcticDB(有版本的 DataFrame)

ArcticDB 是為有版本的時間序列儲存而設計的:
- 「DataFrame 的 Git」——版本歷史、時光回溯
- 針對金融時間序列最佳化
- LMDB 後端(本機)、S3/Azure(雲端)

ArcticDB 回答了讀取與彙總,但沒有回答範圍查詢。它在伺服器端的 `date_range` 篩選是依 datetime *索引*運作的,而這份 panel 是把 `timestamp` 當成欄位,也就是標準的結構;要把篩選下推,就需要與上面計時的寫入配置不同的配置。所以 ArcticDB 不出現在範圍查詢那一格,而不是用其他引擎都不必付出的用戶端篩選來為它計時。
=====a8e8ef3d

# 第 2 部分:伺服器資料庫(需要 Docker)
---
=====2ba73c22
## ClickHouse(OLAP 分析)

ClickHouse 擅長:
- 大規模彙總(每秒數十億列)
- 欄式壓縮(10–15 倍)
- 原生 ASOF JOIN
=====b1582ea0
## QuestDB(高吞吐量時間序列)

QuestDB 針對以下情境最佳化:
- 超高速匯入(透過 ILP 每秒超過 100 萬列)
- 時間序列專用的 SQL 擴充(SAMPLE BY)
- 原生 ASOF JOIN
=====4272c8a5
QuestDB 是透過 ILP 匯入的,而 ILP 會在資料列可以查詢之前就回覆確認。因此 WAL 的提交是在計時區域*之內*輪詢的,這樣 QuestDB 的寫入就結束在與 PostgreSQL 相同的地方:資料可以被讀回來的時候。以前的做法是在計時呼叫之外固定睡眠一段時間,那等於完全沒有向 QuestDB 收取持久性的成本。

panel 是整塊交給 `Sender.dataframe` 的,所以 QuestDB 沒有付出逐列的 Python 成本,也不會出現在用戶端成本的表格中。
=====f6b5cb73
## TimescaleDB(PostgreSQL + 時間序列)

TimescaleDB 結合了 PostgreSQL 與時間序列的最佳化:
- Hypertable(自動分割)
- 用於彙總的 time_bucket()
- 完整的 SQL + 關聯完整性
=====99afe63e
### TimescaleDB 寫入

`execute_values` 接收的是一連串 Python tuple,所以在任何資料到達伺服器之前,panel 必須先被轉成每列一個 tuple。這項建構使用的是 `itertuples`,不是 `iterrows`:`iterrows` 會先把每一列裝箱成一個 Series,產生相同的 tuple 卻要多花一個數量級的成本。這個差異來自 pandas 而不是資料庫,而它以前被算在這個引擎的寫入長條上。下面的儲存格會印出這次執行中這項建構花了多少時間。

關於大小,使用的是 `hypertable_size()` 而不是 `pg_total_relation_size()`:hypertable 的資料列存在子區塊中,所以父關聯是空的,`pg_total_relation_size` 回報的會是大約 16 kB 的目錄額外負擔,而不是資料。
=====915277d4
## PostgreSQL(原生關聯資料庫基準)

原生的 PostgreSQL 作為關聯式的基準:SQL 介面與 TimescaleDB 相同,但沒有 hypertable、壓縮或時間序列函式。這個比較能單獨看出 TimescaleDB 的時間序列擴充在同一個引擎上帶來了什麼。
=====c28acc14
### PostgreSQL 寫入

與 TimescaleDB 相同的 `execute_values` 介面,所以有同樣的逐列 Python 建構,以同樣的方式建立,並基於同樣的理由單獨量測。
=====f72cd0d7
## InfluxDB(時間序列資料庫)

InfluxDB 是專為時間序列打造的資料庫,採用以標籤(tag)為基礎的資料模型與 Flux 查詢語言。我們測試的是透過 Python 用戶端的 line protocol 寫入、整個 bucket 的 Flux 讀取,以及透過 `aggregateWindow` 做每分鐘彙總、再用 `pivot` 合併回來。
=====d13e6002
### InfluxDB 寫入

line protocol 用戶端每列需要一個 `Point`,所以 InfluxDB 和 PostgreSQL、TimescaleDB 一樣要付出逐列的 Python 成本,而且同樣包含在計時的寫入之內並單獨量測。輪詢到第一次可查詢也在計時區域之內,所以這次寫入與其他每一次都結束在同一個事件:資料列可以讀取。在計時呼叫之外固定睡眠,等於完全沒有向 InfluxDB 收取讓它顯得很快的「提早確認」行為的成本。
=====32dfef0d
每個 InfluxDB 的控制代碼一用完就立刻釋放,而不是留給直譯器處理。用戶端會在它的解構子中登出,而等到直譯器進行清理時,登出所需的模組全域變數已經不在了:任何殘存的控制代碼這時都會變成最後一個儲存格執行完之後,出現在 stderr 上的一段錯誤追蹤。

彙總是依日分桶,並對每個欄位使用 OHLCV 正確的彙總方式(first、max、min、last、sum),這也是 TimescaleDB、QuestDB 與 PostgreSQL 所計算的。對所有欄位只做一次 `last()`,對 open、high、low 與 volume 來說在語意上是錯的,而且相對於做混合彙總的引擎會快得不合理。
=====202bd3fb
## kdb+/PyKX(高頻交易的業界標準)

kdb+ 是高頻交易的業界標準:
- 記憶體內的欄式儲存
- 原生 ASOF join(`aj` 函式)
- 用於陣列程式設計的 q 語言

**設定**:需要位於 `~/.kx/bin/q` 的獨立 q 執行檔,以及位於 `~/.kx/` 或 `~/.pykx/` 的有效授權。個人授權可從 kx.com 取得。

我們使用 IPC 模式(連線到外部的 q 行程),而不是 PyKX 內嵌的 q,因為它的授權處理比較可靠,也更能反映正式環境的用法。
=====8a561da3
kdb+ 的寫入是用 `set` 把一個 splayed 資料表持久化到磁碟,這是使用 kdb+ 的團隊持久化資料表的做法,而且結束時資料已在磁碟上。以前計時的是 `-8!`,也就是記憶體內的 IPC 序列化,並把它稱為寫入,而同一張圖上的其他每個引擎都是寫到磁碟或伺服器。那是不同的操作,這也是為什麼 kdb+ 曾經看起來比其他任何引擎快約四十倍:它根本沒有在做那件工作。`.Q.en` 會把代號欄位對照 sym 檔做列舉,這是 splayed 資料表所要求的,而整個持久化過程都在計時區域之內。

### 圖表

同一格中的每個引擎都是在開頭所述的同一套讀取政策下計時的,所以同一格內的長條可以互相比較。每一格會依它實際擁有的長條,選擇自己的 x 軸刻度:差距大時用對數軸,讓短的長條仍然看得清楚;差距小時維持線性,讓長條的長度仍然與時間成正比。在對數軸上,長條是從軸的下限而不是從零開始,所以兩倍的差異看起來會大得多;依量測到的差距而不是記憶中的差距來選擇座標軸,可以避免在回應的引擎組合不同時發生這種情況。

## 重點整理

這裡沒有指名哪個引擎最快。每項操作由哪一個回答得最快印在上面,那是這次執行在你的硬體上的結果,可能與我們的不同。能跨次執行通用的,是答案的形狀:

1. **儲存配置決定了掃描成本。** 把同一欄存在一起、並以批次方式執行的引擎,讀取分鐘 panel 的方式,與把同一列存在一起、為了回答關於兩個欄位的問題卻必須碰到全部九個欄位的引擎不同。這條分界——一邊是 DuckDB 與 ClickHouse,另一邊是 SQLite 與 PostgreSQL——是關於引擎如何建造的事實,也是看全表掃描那一格時首先要注意的。
2. **範圍查詢與掃描是不同的問題**,而它正是回測會問的那一個。上面的視窗涵蓋 panel 最前面的幾個交易日;定義它的儲存格會印出那最後佔了多少比例的資料列。能依時間分割做裁剪、或走訪依時間排序的索引的引擎,不必讀取其餘部分就能回答,而掃描後再篩選的引擎則不行。只依全表掃描排名會掩蓋這個差別。要留意那個比例:如果視窗涵蓋了整個 panel,圖表左邊的兩格量測的就是同一個查詢。
3. **匯入速率與持久性是一個數字,不是兩個。** 這裡每個寫入時間都結束在資料可以查詢的時候,這就是為什麼提早確認的引擎——透過 ILP 的 QuestDB、InfluxDB——看起來並不是零成本。
4. **每根寫入長條中都含有用戶端;其中三個讓你看得到含了多少。** PostgreSQL、TimescaleDB 與 InfluxDB 是透過每列需要一個 Python 物件的介面連線的,而建立那些物件是一個可以單獨計時的獨立運算式。圖表上方的表格給出了那個時間。沒有出現在其中的引擎並不是沒有用戶端成本——它們的轉換發生在同時執行寫入的那個呼叫之內,無法分離出來——所以要把那張表讀成三個下界,而不是把所有引擎分成兩類。
5. **比較的品質取決於它的政策。** 上面的每個數字,對每個引擎都是一次冷寫入與暖讀取的平均。暖讀取對任何有緩衝池的引擎都有利;在冷快取或跨網路的情況下,有壓縮的引擎會佔上風。做選擇之前,請在你自己的匯入路徑上重新執行。

**kdb+/PyKX** 除非你提供 q 執行檔與授權,否則會被跳過,所以除非你有設定,上面的數字中不會有它。本章有討論它適合用在哪裡;本筆記本不會宣稱一個它沒有量測過的結果。
