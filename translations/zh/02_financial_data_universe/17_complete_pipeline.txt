# 完整的資料管線:從多來源取得到可供 ML 使用的資料

**Docker 映像檔**:`ml4t`

## 目的
把本章的各個元件——多供應商資料取得、OHLC 驗證、來源標註與有效率的儲存——串接成兩條端到端的管線:一條股票管線,把 WikiPrices(1990–2018)與 Yahoo(2018 至今)拼接起來;一條加密貨幣管線,使用本機的 Binance 小時永續合約 panel。接著筆記本會展示 `ml4t.data.DataManager` 如何用一小部分的程式碼完成同樣的工作。

## 學習目標
- 建立多來源的股票管線,並在每個邊界進行驗證。
- 偵測全天候市場的涵蓋缺口,並為加密貨幣資料加上交易時段特徵。
- 為每一列標註它的來源,讓多來源資料可以被稽核。
- 用 `ml4t.data` 隨附的 `DataManager` + `Universe` + `HiveStorage` 高階 API 取代明確寫出的管線。

## 書籍對照
第 2 章 §2.3(多來源拼接 + 正式環境的管線)。管線的輸出會供應 ETF 與加密貨幣永續合約的案例研究。

### 宣告的參數

`AS_OF_DATE` 固定了每個視窗的右端,這樣輸出在書的各版本之間是穩定的,而不會隨著系統時鐘變動。

## 1. 管線架構

正式環境的管線有三個階段:

| 階段 | 輸入 | 輸出 |
|-------|--------|---------|
| **取得(Acquire)** | Yahoo Finance、WikiPrices、Binance | 各來源的原始 OHLCV |
| **處理(Process)** | 原始 OHLCV | 經驗證、標準化、標註的資料表 |
| **儲存(Store)** | 已標註的資料表 | 依代號/日期分割的 Parquet |

有四項設計原則貫穿筆記本的其餘部分:

1. **供應商獨立性**——協調程式不應該在意每一列來自哪個來源。
2. **在邊界驗證**——每個進入/離開的點都檢查 OHLC 不變條件、缺口門檻與重複的時間戳記。
3. **來源標註**——每一列都帶有 `source` 欄位,讓下游除錯不至於抓狂。
4. **增量更新**——重新執行時只抓取新的部分(§5 的 `DataManager` API 會自動處理這件事)。

## 2. 股票管線

### 接縫需要重新縮放,不只是篩選

在邊界有兩件事必須協調,而第一件是機械性的。兩個供應商對時區的處理不一致——一個的時間戳記不帶時區,另一個帶 UTC 時區——所以把兩段串接時會報錯,而不是默默地混用兩個時鐘。這個拒絕是對的,但問題仍然要解決:兩者都是 UTC 的日 K 棒,所以轉換成 UTC 再拿掉時區,就能把它們放到同一個時鐘上,而不會移動任何東西。

兩個資料饋送都發布調整後價格,但它們是針對不同的事件集合做調整的。WikiPrices 只回溯調整發生在它自己涵蓋期間內的分割,而那段期間止於 2018 年。Yahoo 則回溯調整到今天為止的每一次分割,包括那個日期之後的——其中就有蘋果 2020 年的一拆四。因此,把兩段在接縫處篩選後串接,會產生一個帶有跳階的序列,而那個跳階是公司行動,不是價格變動。

修正方式只需要一個數字,而在哪裡量測它比看起來更重要。兩段都已經做過股利調整,所以在*兩個*資料饋送都有報價的任何一天,它們兩個收盤價的比值就是調整基準的差異,別無其他。如果改成跨越接縫取比值——歷史段的最後一個收盤價對近期段的第一個——就是把兩個不同日子的價格相除,於是中間的市場變動也被帶進了這個因子裡。這會迫使跨越接縫的報酬變成零,並把同樣的變動推到重新縮放後的成交量裡。

所以近期段是從 `OVERLAP_START` 開始抓取的,在接縫之前而不是之後,純粹是為了讓兩段有共同的日期可供量測;因子取自兩者都有報價的最後一天,而合併兩段時再把重疊的列從歷史段那一側去掉。成交量的縮放方向相反——一拆四的分割讓價格變成四分之一、股數變成四倍——所以歷史成交量要除以同一個數字。

合併步驟會斷言重疊區間不是空的,因為如果抓取的視窗沒有重疊,因子就不會被設定,重新縮放會被默默跳過,而那看起來和「不需要重新縮放的拼接」一模一樣。

## 4. 儲存的最佳實務

### 分割的 Parquet 儲存

對於大型資料集,依時間與代號分割:

```
output/
└── etf_momentum/
    ├── year=2024/
    │   ├── SPY.parquet
    │   ├── QQQ.parquet
    │   └── TLT.parquet
    └── year=2023/
        └── ...
```

**好處**:
- **分割裁剪(partition pruning)**:只讀取需要的日期範圍
- **增量寫入**:新增資料時不必重寫
- **平行讀取**:同時處理多個分割

## 5. 用 DataManager 簡化

=====c892f365
DataManager 的版本用幾行程式碼取代了約 100 行手動建立供應商實例、合併資料與驗證的程式碼。它在底層使用的是相同的供應商與驗證——完整的逐步說明請見筆記本 `17_data_management` 與 `18_incremental_updates`。
=====4a31dcfb
## 重點整理

1. **拼接的是兩種調整基準,而不是兩段日期範圍。** 把每個資料饋送在接縫處篩選後串接,只要有公司行動發生在較舊的資料饋送停止之後,就會留下一個跳階,因為較舊的資料饋送無法為它從未見過的事件做回溯調整。兩段都已做過股利調整,所以在接縫處的一個比值就能消除差異,而成交量則取同一個因子的倒數。

2. **為每一列標註來源。** `source` 欄位讓接縫在上面的圖中看得見,讓供應商不一致的問題可以除錯,也讓資料遷移可以逆轉。它的成本只是一個欄位。

3. **驗證器必須配合它所驗證的資料節奏。** 股票管線把多日的缺口視為異常,加密貨幣管線則把超過一根 K 棒的缺口視為異常,因為股票的行事曆會休市,而永續期貨市場不會。把任何一個門檻用在另一個 panel 上,不是把行事曆回報成故障,就是漏掉每一次中斷。

4. **股票驗證器找到的缺口就是行事曆,而它無法告訴你這一點。** 每個代號被標記的缺口都是同一次市場休市,那是關於 2001 年 9 月的事實,而不是關於資料饋送的事實。缺口偵測器能定位出一個不連續點;要判定那是什麼,則需要行事曆。

5. **等管線不再變動之後,再升級到 `DataManager`。** 上面明確寫出的類別,是為了展示高階 API 在做什麼。第 5 節用它重現了同樣的工作,而正式環境走的是較短的那條路。
