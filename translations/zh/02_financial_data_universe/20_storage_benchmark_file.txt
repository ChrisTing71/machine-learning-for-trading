# 檔案格式儲存效能測試

**環境**:鎖定的環境(`uv run`)——見下方的先備條件。

**目的**:在同一份 100 萬列的 OHLCV panel 上,沿著三個面向比較 CSV、Parquet、Feather(Arrow IPC)與 HDF5——寫入時間、讀取時間(強制實體化)與磁碟上的大小——讓 §2.4 中的取捨可以從頭到尾重現。

**學習目標**:
1. 產生一份確定性的 OHLCV 測試 panel,規模為第 §2.4 節引用的 L 級(100 個代號 × 10,000 根一分鐘 K 棒 = 1,000,000 列)。
2. 在一套明確說明的計時政策下,為每種格式的寫入與讀取計時。
3. 對 Feather / HDF5 的讀取強制實體化,這樣記憶體映射或延遲讀取就不會偽裝成瞬間完成。
4. 量化欄位投影(columnar projection)的好處(讀 2 欄對上讀 9 欄)。
5. 繪製三格的比較圖(讀取時間/寫入時間/檔案大小)。

**書籍對照**:§2.4——以檔案為基礎的儲存效能測試。

**先備條件**:PyTables(HDF5 的後端)已包含在鎖定的環境中,所以從儲存庫根目錄執行 `uv run python 02_financial_data_universe/20_storage_benchmark_file.py` 就是這本筆記本所需的全部——不像 `21_storage_benchmark_database` 那樣需要資料庫服務。

> **數字是由哪個環境產生的**:鎖定的環境(`uv sync`,也就是 `uv.lock`),這是 §2.4 所報告的。`benchmark` Docker 映像檔目前解析到的 pandas 版本比 `uv.lock` 鎖定的*更新*,而 pandas 較新的字串型別讓 PyTables 儲存低基數的 `symbol` 欄位時,每列寬了大約 8 個位元組——足以讓同一份 panel 的 HDF5 檔案從約 71 MB 變成約 79 MB。CSV、Parquet 與 Feather 不受影響。請在 `uv run` 底下執行本筆記本,以重現 §2.4。

## 計時政策

下面的每個數字都遵循同一套政策,並且一視同仁地套用在四種格式上。如果在比較的對象之間混用不同的政策,那就不算是比較,所以這裡把它先說清楚,而不是留在各個呼叫處:

- **寫入**(`time_write`)——只做一次,沒有暖身執行。寫入 panel 是每個資料集只做一次的操作,所以我們計時的就是這個。
- **讀取**(`time_read`)——在一次不計時的暖身執行之後,取 `TIMING_RUNS` 次執行的平均。**這些是暖快取(warm-cache)的數字。** 檔案才剛被寫入並反覆重讀,所以它位在作業系統的頁面快取中。

暖快取讀取如實描述了研究迴圈實際上的*重複存取*模式,但它對記憶體映射格式有利:Feather 映射的是已經常駐在記憶體中的頁面,所以它下面的讀取數字接近最佳情況。從磁碟第一次讀取冷檔案時,它與 Parquet 的差距會縮小;而在網路或物件儲存上,壓縮格式通常會直接勝出,因為它搬移的位元組比較少。這裡的排名適用於暖的、本機的、重複的讀取——這也是 §2.4 為這些數字附上的但書。
=====c1071701
## 1. 產生測試 panel

`generate_ohlcv_data` 回傳一份確定性的 OHLCV panel:在固定種子下各代號的隨機漫步,這樣格式之間的比較不會因為各次執行的資料漂移而混淆。在 L 規模下是 100 個代號 × 10,000 根一分鐘 K 棒 = 總共 100 萬列,分布在 26 個正常交易日(每日 390 根 K 棒)上,所以這份 panel 帶有真實分鐘資料會有的隔夜與週末缺口。所有代號共用同一個交易時段格點,就像任何同步的 K 棒 panel 一樣。
=====921202f9
## 2. CSV——通用的基準

CSV 是以列為導向的基準:人類可讀、沒有壓縮、沒有結構定義。其他每種格式都是對照它來評斷的。
=====ab3f66bc
## 3. Parquet——壓縮的欄式標準

Parquet 的列群組(row-group)配置、字典編碼與 Snappy 壓縮,讓它成為分析型工作負載的預設選擇。欄位投影只會讀取所要求欄位的列群組區塊。
=====6559e2a0
## 4. Feather(Arrow IPC)——零複製的資料交換

Feather 是以記憶體映射的方式開啟檔案;單純的 `read_ipc` 呼叫幾乎立刻就回傳,因為還沒有任何位元組被讀取。我們同時記錄原始的開啟時間,以及把欄位實際實體化到記憶體中的時間。只有實體化後的數字才能跨格式比較。
=====dbe675c9
## 5. HDF5——舊式的科學運算容器

HDF5 在早於 Parquet 的研究程式碼庫中仍佔有一席之地。`pandas.HDFStore` 使用的 `fixed` 格式不支援欄位投影,所以為了公平起見,我們把欄位讀取記錄成與完整讀取相同。

## 重點整理

- **記憶體映射不算是讀取。** 原始的 Feather 控制代碼幾乎立刻就回傳,因為還沒有碰到任何東西;成本是在頁面第一次被存取時才出現。實體化讀取才是把四種格式放在同一個基準上的比較,也是上面所畫的那一個。
- **沒有任何格式在三格圖中全部勝出。** 讀取最快的、寫入最快的與磁碟上最小的並不是同一種格式,所以選擇是一種取捨而不是排名,而哪個面向才是關鍵,取決於這份 panel 是寫一次後不斷讀取,還是要在網路上搬移。
- **欄位投影是欄式格式快的原因,而 CSV 沒辦法有這個功能。** 在 Parquet 與 Feather 上,只讀取幾欄而不是整個結構,成本大致與所要求的欄數成正比。CSV 幾乎沒有受益,因為要讀到某一列中較後面的欄位,就得先解析它前面的每一個欄位。
- **壓縮縮小的是檔案,不是資料表。** Parquet 寫出的 panel 只有 CSV 大小的一小部分,而讀回之後在記憶體中佔用的空間是一樣的,因為兩者都落在相同的 Arrow 緩衝區中。格式的選擇是關於磁碟與網路的決策,它並不會改變資料載入之後的成本。
- **HDF5 的 fixed 格式是一次到位的。** 它可以讀取或寫入整份 panel,但不提供欄位投影。

### 格式選擇

- **長期儲存、雲端、跨語言**:Parquet。
- **Python 工具之間的本機資料交換**:Feather。
- **需要附加寫入的舊式科學 Python 管線**:HDF5。
- **人工檢視或小量匯出**:CSV。
