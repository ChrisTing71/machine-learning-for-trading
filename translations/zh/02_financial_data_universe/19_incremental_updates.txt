# 增量更新:讓市場資料保持最新

**Docker 映像檔**:`ml4t`

**目的**:逐步走過更新的生命週期——初次載入、每日增量、缺口偵測,以及一個小型的健康狀態儀表板——讓 `data/download_all.py --update` 中執行的同一套流程從頭到尾都看得見。

**學習目標**:
1. 比較完整重抓與增量更新的成本。
2. 用 `DataManager.update(..., fill_gaps=False)` 驅動每日增量,並理解為什麼預設的 `fill_gaps=True` 對 OHLCV 資料並不安全。
3. 用 `GapDetector(exclude_weekends=True)` 驗證完整性。
4. 繪製三格的健康狀態儀表板(資料量、新鮮度、問題)。

**書籍對照**:§2.4(儲存資料)——是筆記本 20 與 21 中儲存效能測試在營運面的對應。

**先備條件**:已安裝 ml4t-data;可即時連線到 Yahoo Finance。

**為什麼要增量更新**:完整重抓會重新抓取一個代號有史以來的每一列,而增量執行只抓取上次之後的交易日。在一個有數百個代號、十年歷史的股票池上,前者是數百萬列,後者是數百列,而且每天如此。第 1 節會在示範股票池上量測這個比例。

### 步驟 2:增量更新(只有新資料)

更新時會讀取儲存中的最後一個時間戳記,重新抓取一小段重疊區間(`UPDATE_LOOKBACK_DAYS`),讓供應商修訂過的 K 棒取代已儲存的那一根,然後合併之後的所有資料。

**它在哪裡停下來,比它從哪裡開始更重要。** Yahoo 會把目前的交易所日期回傳成一列成交量持續累積、但沒有開高低收的資料。沒有價格的 K 棒不算是 K 棒,而供應商類別也是這麼說的:

```
DataValidationError: yahoo: Column 'open' contains 1 null values
```

`DataManager.update()` 會抓取到 `datetime.now()`,所以它在每個交易日都會要求那一列,然後報錯。`update_through_last_complete_bar` 執行的是同樣的增量,但它是**找出**視窗的終點,而不是計算出一個。它從目前交易所日期的前一天開始——以交易所時間計,不是 UTC,因為紐約晚上 22:00 時 UTC 日期已經是明天了——只要供應商拒絕該視窗,就一次往回退一天。

這種回退是光靠日期做不到的。佔位列通常在收盤後幾小時就會補上,但有時不會:Yahoo 的 AAPL 2026-09-03 日 K 棒在八個半小時之後仍然是 `NaN, NaN, NaN, NaN, 37197362`,而結束於 2026-09-02 的同一個視窗每一欄都是乾淨的。從行事曆來看兩者一模一樣,所以必須去問供應商。

當某個視窗被拒絕時,ml4t-data 會以 error 層級記錄。如果你在下面看到 `Failed to fetch AAPL: yahoo: Column 'open' contains 1 null values`,而下一行是一個列數,那就是回退機制在運作:第一個視窗要求了一根供應商尚未發布的 K 棒,第二個視窗則成功了。

不要盲目呼叫 `update()` 的另一個理由是它預設的 `fill_gaps=True`:那是一個不懂行事曆的缺口偵測器,會把每個週末與美國假日都當成缺少的交易日並向前填補,讓每個代號的列數多出數百根幽靈 K 棒。對 OHLCV 資料來說,正確的做法是讓非交易日保持不存在,並在下游依靠懂行事曆的完整性檢查——這就是第 3 節用 `GapDetector` 所做的事。
=====a5313709
每個代號一開始有 502 列(2023-01 到 2024-12)。更新會抓取 7 天的重疊區間,加上直到最後一根完整 K 棒為止的每個交易日,然後合併;得到的列數等於原本的 502 加上恰好是新的交易日數——沒有合成的週末/假日資料列,也沒有為仍在進行中的交易日產生的半成品 K 棒。

## 3. 缺口偵測

在執行回測之前,先驗證你的資料是完整的。缺口可能來自下載失敗、供應商中斷,或假日的處理方式。
=====cc4122a8
`exclude_weekends=True` 會濾掉週六與週日。美國市場假日(馬丁路德金恩紀念日、耶穌受難日、感恩節等)仍然會被記為一日的缺口,因為偵測器沒有交易所行事曆——這對例行的更新健康檢查來說沒問題,但在把結果用於回測 panel 之前,要再搭配懂行事曆的完整性檢查。

## 5. 本書的更新流程

本書的 `data/download_all.py` 腳本正是為所有資產類別實作這個模式。加上 `--update` 執行,就能把資料集延伸到現在:

```bash
# 初次下載(執行一次)
python data/download_all.py

# 更新到現在(每天/每週執行)
python data/download_all.py --update
```

在底層,`download_all.py` 使用:
- `ETFDataManager.from_config("data/etfs/config.yaml")` → `manager.update()`
- `CryptoDataManager.from_config("data/crypto/config.yaml")` → `manager.update()`
- `MacroDataManager.from_config("data/macro/config.yaml")` → `manager.download_treasury_yields()`
- `FuturesDataManager.from_config("data/futures/config.yaml")` → `manager.download_all()`

每個管理器會讀取它的 YAML 設定檔,取得代號、日期範圍與供應商設定,然後只更新新的部分。

### 由設定檔驅動的下載

位於 `data/etfs/config.yaml` 的 ETF 設定檔定義了:
```yaml
etfs:
  provider: yahoo
  start: '2006-01-01'
  end: '2025-12-31'
  frequency: daily
  tickers:
    us_equity_broad:
      symbols: [SPY, QQQ, IWM, ...]
    us_sectors:
      symbols: [XLB, XLC, XLE, ...]
    # ... 9 個類別,共 100 檔 ETF
```

當你在 2026 年以後以 `--update` 執行時,它會把資料延伸到設定的結束日期之後、直到現在——不需要更改設定檔。

## 總結

### 主要模式

| 模式 | 指令 | 時機 |
|---------|---------|------|
| 初次載入 | `dm.load(symbol, start, end)` | 第一次 |
| 每日更新 | `dm.update(symbol, lookback_days=7)` | 每個交易日 |
| 缺口檢查 | `updater.detect_gaps(df, "daily")` | 回測之前 |
| 完整重抓 | `UpdateStrategy.FULL_REFRESH` | 資料損毀之後 |
| 批次更新 | `download_all.py --update` | Cron 排程 |

### 正式環境檢查清單

1. **初次下載**:`python data/download_all.py`(執行一次,約 10 分鐘)
2. **排程更新**:把 `download_all.py --update` 加入 cron(每天下午 6 點)
3. **監控健康狀態**:在回測之前檢查新鮮度、缺口與驗證結果
4. **驗證資料**:每次載入都使用 `OHLCVValidator`(見 `13_data_quality_framework`)

### 重點整理

- **`lookback_days` 才是操作上的槓桿**,不是代號集合。把它設定一次,涵蓋供應商的修訂視窗(Yahoo 會回溯調整約 5 個交易日;CRSP 約 30 個),這個策略就能通用於各種金融工具。
- **缺口偵測是對已儲存的資料執行的,不是對串流資料。** 每日的 cron 排程以 `detect_gaps()` 作結,就能在任何回測讀到過時的分割之前,抓出漏掉的交易日。
- **完整重抓是復原的途徑。** 當驗證標示出資料退化時,使用 `UpdateStrategy.FULL_REFRESH`;絕對不要就地修補損毀的 parquet 檔。
- **可設定的結束日期消除了設定檔漂移。** 代號清單的 YAML 以今天為預設值;`--update` 會把資料延伸到檔案的 `end:` 欄位之後,不需要每個日曆年都去編輯。
- **Cron 加上冪等的 CLI 就是正式環境的介面。** 同一個 `download_all.py --update` 在筆記本、CI 執行與下午 6 點的 cron 中都能運作。

接下來:`20_storage_benchmark_file` 比較各檔案格式的吞吐量,這關係到每次更新中隱含的 parquet 寫入路徑;`21_storage_benchmark_database` 則把同樣的比較延伸到資料庫引擎。

### 交叉參照
